# 02 · 综合/实现报告排障（提示词工作流）

## 适用范围

`report_utilization` 或 `report_timing_summary` 出来后，需要判断「到底是谁卡住了」，
并决定下一步改哪个参数。适用于 Vivado / Quartus 这类以资源表 + 时序报告为主的流程。

## 输入

从报告里**原样复制**这几段（不要只给百分比，要带分子分母）：

```
1. Utilization: Slice LUTs / Slice Registers / Block RAM Tile / DSP48E1（used/available）
2. Timing: WNS / TNS / WHS / THS，以及 WNS 最差路径的 Startpoint → Endpoint
3. 时钟：create_clock 周期、实际约束的时钟名
4. 设计规模：顶层模块、关键 IP（HLS 生成的 IP 名）
```

## 步骤

**第一步：定瓶颈**
> 这是 <器件> 的实现报告摘要。请按「先看不可替代资源、再看可替代资源」的顺序，
> 判断哪一类资源最先撞上限：DSP（算法必需）→ BRAM（缓冲必需）→ LUT（可被综合器重构）。
> 给出排序依据，并指出当前设计距离下一个瓶颈还有多少余量。

注意：**DSP 100% 不一定是坏事**，如果算法本身就要这么多乘累加，说明芯片被用满了；
真正的问题是 LUT 或 BRAM 先撞上限时，综合器会为了省它们牺牲频率。

**第二步：解释时序违例**
> WNS 为负，最差路径是 <startpoint> → <endpoint>。请判断这条路径属于：
> 组合逻辑过深 / 布线拥塞 / 跨时钟域 / 高扇出控制信号，并给出对应的修改方向。

把路径贴出来是关键 —— 只说「时序不收敛」模型只能给出通用建议。

**第三步：给出取舍表**
> 请列出 3 个可选的修改方案，每个方案说明：改什么参数、预计省多少资源或多少 ns、
> 对吞吐的影响、引入的新风险。

**第四步：验证假设**
改完一轮后，把新旧报告一起贴回去：
> 上一轮我们把 <X> 改成 <Y>，WNS 从 <a> 变为 <b>，DSP 从 <c> 变为 <d>。
> 这符合预期吗？如果不符合，说明我们对瓶颈的判断错在哪？

## 输出物

瓶颈排序 + 修改方案对照表 + 每轮的预测与实测差异记录。这份记录本身就是设计报告
「优化过程」一节最好的材料。

## 验收

- 每一轮的预测（改哪里、会怎样）与实测结果都有对照；
- 最终资源表与设计报告中声明的一致；
- 时序收敛后，WNS 与时钟频率、保持时间裕量都能在报告里找到对应行。

## 失效条件

- 报告被截断（只给了百分比没给分母）—— 判断会失真，尤其是 LUT 与 Slice 的区别；
- 设计含多个时钟域 —— 单看 WNS 会漏掉跨域路径，需要看 CDC 报告；
- 用了 HLS 综合的 IP —— 其内部时序由 HLS 报告决定，Vivado 报告看不到内部路径。

## 已验证效果

在本作品上按此流程定位到：DSP 先满（220/220），此时 LUT 82%、BRAM 77% 仍有裕量，
因此不再提高并行度，而是把优化方向转到访存重叠（乒乓缓冲）上；
最终在 120 MHz 下 WNS +0.189 ns 收敛。

## 常见误判

| 现象 | 常见误判 | 实际原因 |
|---|---|---|
| DSP 100% 但吞吐上不去 | 并行度不够 | 访存带宽或乒乓缓冲没做，阵列在等数据 |
| LUT 90%+ 且时序变差 | 逻辑写多了 | 综合器为了省 BRAM 把表展开成 LUT |
| WNS 为正但仍不稳定 | 时序已收敛 | 跨时钟域或约束缺失（false path 没写） |
