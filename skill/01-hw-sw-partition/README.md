# 01 · 软硬件划分与并行度定标（提示词工作流）

## 适用范围

手上有**算法描述 + 一块具体器件**，需要决定：哪些放 PL、哪些放 PS、加速器做多少路并行、
片上缓冲怎么组织。适用于 CNN、图像处理、矩阵运算这类规则数据流；不适用于控制律、
分支密集的状态机、动态 shape 的网络。

## 输入（必须写全，缺一项模型就只能给套话）

```
1. 算法：层类型、输入尺寸、通道数、权重规模、算子列表
2. 设备：器件型号、DSP 数量、BRAM 数量、LUT 数量、可用时钟频率
3. 约束：目标帧率 / 吞吐、单帧允许延迟、功耗上限
4. 外部存储：DDR 位宽与频率、可用的 AXI 主口数量
5. 谁做控制：是否有 CPU（Zynq / SoC）可承担非规则逻辑
```

## 步骤

**第一步：划分（先粗后细）**
> 下面是一个图像推理任务，器件是 <器件型号>，资源 <DSP/BRAM/LUT>。
> 算法是 <逐层描述>。请给出软硬件划分：每个算子归属 PL 还是 PS，理由是什么，
> 并指出哪些算子的数据量太大、必须留在 DDR 而不是片上。

要求模型对**每个算子**给出「计算量 / 访存量」的粗估，而不是只给结论。
判据是算术强度：计算远大于访存的算子才值得进 PL。

**第二步：并行度定标**
> 加速器要放满 DSP，请按「一个 DSP 承担一次 16 位乘累加」计算最大并行度，
> 再按输出通道 × 输入通道拆成二维阵列。给出 (输出通道, 输入通道) 的组合表，
> 每种组合的 DSP 占用、片上缓冲需求、理论周期数，以及哪个组合能在 <时钟> 下达到 <目标延迟>。

关键动作：**让模型列成表**。我们最终选的 32 输出 × 4 输入 = 128 路，
就是在这张表里反复权衡后定下的 —— 单看「最大并行度」会得到更大的数，但片上缓冲放不下。

**第三步：分块与缓冲**
> 按上一步的并行度，输出特征图要分成多大的 tile 才能让片上缓冲装下？
> 输入、权重、输出三者各自的复用关系是什么？需要几组乒乓缓冲才能把加载、计算、写回重叠？
> 如果 tile 变小会导致 DDR 访问次数上升，请给出访存次数的估算和它会不会成为瓶颈。

**第四步：让模型自我反驳**
> 请指出上面的划分里有哪一步是全片最可能卡住的地方（DSP / BRAM / 带宽 / 时序），
> 并给出「如果它真的卡住了，应该先改哪个参数」的备选方案。

这一步产出的是**排障顺序**，不是新的架构。没有它，上板卡住时只能瞎试。

## 输出物

一份划分表 + 并行度参数表 + 缓冲组织图 + 瓶颈排序。可直接作为设计报告
「软硬件划分依据」一节的内容。

## 验收

- 并行度表里每一行都能算出 DSP 数并与器件上限对得上；
- 缓冲需求能用「tile 尺寸 × 通道数 × 位宽」算出手算值；
- 瓶颈排序在综合实现之后能被验证（若实际瓶颈与预测不符，记录下来改进提示词）。

## 失效条件

- 算法含大量控制流分支、动态 shape、稀疏结构 —— 规则阵列不适用，需改用数据流架构；
- 器件没有 DSP 或 DSP 位宽不匹配（如 8 位量化落在 DSP48 上需 packing）—— 需重算；
- 带宽受限远超计算受限（如每层都要全图重读）—— 此时并行度再高也无意义，应先改数据复用方案。

## 已验证效果

用本提示词在同一块 xc7z020 上得到 32×4=128 路并行、13×13 输出分块、三组乒乓缓冲的结构，
实现后 DSP 占用 220/220，整网 429 ms/帧。瓶颈排序（DSP 先满、其次 BRAM、最后时序）
与实现报告一致。
