# 大模型协作记录

对应竞赛指南 3.3.5.3「大模型协作记录」。内容来自实际交互，提示词经脱敏与合并同类项，
保留当时的约束条件与判断依据。

---

## 一、协作方式与约束

| 任务 | 模型承担 | 人承担 |
|---|---|---|
| 文档与图表 | 结构化写作、Pillow 绘图脚本、排版 | 指标数值与口径判断 |
| 代码与脚本 | 权重导出、校验脚本、测试台框架 | 算法结构与硬件微架构决策 |
| 排查与复现 | 从日志定位方向、给排查顺序 | 最终判断（回到板上验证） |

每次对话重新声明三条约束：

1. 文档中每个数字必须能追溯到实测日志或工具报告，不得推算或补全；
2. 同一指标只能有一种口径，口径变化必须显式声明（如加速比是单层还是整网）；
3. 不出现学校、姓名等身份信息。

第 2 条是吃过亏之后加的，见 3.2。

## 二、典型提示词

### 2.1 从日志与源码整理技术文档

```
约束：所有数字必须与 data/board_run_log.txt 和源码一致；
不要出现学校名称；图表用脚本生成，不贴截图。
先给章节骨架，并在骨架里列出每一节将引用的数据及其出处。
```

要求「骨架阶段就列出数据出处」这一条，显著减少了后文出现无出处的数字。

### 2.2 定点误差比对

```
这是板上 dump 的单层输出（int16，缩放 512），参考值是 PC 端 float32。
给出误差统计，并判断是整体缩放问题还是个别通道问题。
```

后来固化成 `skill/03-fixed-point-checker/fx_compare.py`，不再每次让模型现算。

### 2.3 排查类提示词的写法

排查问题时，有效的提示词必须包含三件事：现象、已排除的可能、可验证的手段。

```
现象：加速器单层输出与 CPU 参考有 2733 个元素不一致，边缘 327、内部 2406。
已排除：padding 处理、累加顺序、第 4 输入通道越界读、Tn=4 补零引入的额外舍入。
可验证：HLS 源码在 src/hls/，CPU 参考在 bench_cpu.cpp，可在 PC 上仿真任意一段。
问题：还有什么能解释"内部元素也不一致"？
```

只写「为什么对不上」会得到一串泛泛的猜测；写清已排除项之后，模型的回答才开始收敛。

## 三、自我纠错轨迹

### 3.1 定点失配：五次假设被逐一证伪

**现象**：PL 加速器与 CPU 参考实现对同一层卷积的输出不一致，
失配元素数在排查过程中从 182822 降到 5576、再降到 2733，但始终无法归零。

**排查过程**：每个假设都在 PC 上写一段仿真验证，不靠推理下结论。

| 假设 | 验证方式 | 结论 |
|---|---|---|
| padding/边缘处理不同 | 统计失配位置分布 | 否，89% 在内部 |
| 累加顺序导致舍入差异 | 按硬件顺序重排 CPU 累加 | 否，0 处变化 |
| 第 4 输入通道越界读 | 检查权重是否零填充 | 否，已零填充 |
| `Tn=4` 补零引入额外舍入 | 验证 `rnd9(0)=0` | 否，补零不产生舍入 |
| 分块边界未覆盖 | 核对 tile 覆盖范围 | 否，覆盖完整 |

**根因**：HLS 的 `compute()` 里累加器本身就是 `ap_fixed<16,7,AP_RND,AP_SAT>`，
**每乘一项就 round + saturate 一次**，不是先用宽累加器累加、最后统一舍入。
CPU 参考用 int32 累加、最后统一右移，两条舍入路径不同，结果不可能逐位相同。

**修正**：问题不在实现，在验收标准。把「逐位相同」改为「相对误差」，
实测 `rel_mean` 与 `rel_max` 均在可接受范围。

**教训**：异构实现之间要求 bit-exact 是个错误的目标，
定点硬件与软件参考只要舍入策略不同就必然有差异。
纠结了很久才意识到要质疑的是验收标准而不是代码——
**排查前应先问「这个标准本身是否成立」**。已写入 `skill/03` 的失效条件。

### 3.2 加速比被"优化"成虚高 ★

这是最值得记录的一次，因为出错方向对本作品有利。

**经过**：3.1 查明两边舍入路径不同后，一个"自然"的后续动作是让 CPU 参考
复刻硬件的逐项截断，使两边逐位对齐。模型照做并给出了结果：

```
ARM 耗时   874 ms → 1340 ms
加速比     106x  → 162x
```

**问题**：162× 看起来是更好的成绩，但它来自把软件基线**故意写慢**。
逐项 round + saturate 是硬件为了省位宽才做的妥协，软件没有这个约束——
int32 累加既更快又更准，那才是 CPU 真实水平。

公平的问题是「用 FPGA 比**好好写的软件**快多少」，不是「比刻意写坏的软件快多少」。

**修正**：撤回，保留 int32 累加的 874 ms 与 106×。
相应地，验证标准也只能是相对误差（见 3.1）。
基线实现见 `src/ps/bench_cpu.cpp` 的 `cpu_conv_leakyrelu()`：
用 `int acc` 累加、最后统一右移 9 位，而非逐项舍入。

**教训**：当一次改动让自己的指标变好看时，要先问它是否通过降低对照组达成。
模型不会主动质疑对自己任务有利的结果，**这类审查只能由人设为固定检查项**。
已写入 `skill/01` 的验收项：「对比实验中，基线必须是对方能达到的最好水平」。

### 3.3 重复照射：同一株被打两次

**现象**：手工记录显示传送带速度较慢时，同一株杂草会被照射两次甚至三次。

**初步归因（错）**：判重半径 40 px 不够大。按此改大半径后，
动态场景确实好转，但静态场景开始漏打——半径过大会把相邻植株也判成同一株。

**真正根因**：`fire_ticks=1` 时一次照射跨两拍，而 `mark_done`（记入已打列表）
原本放在照射**结束**那一步。进入 FIRING 这一拍激光已经实际点亮约 0.5 s，
但只要下一拍任何一道联锁不满足就会 abort，什么都没记下——
这一株仍然算"没打过"，冷却完又被重新锁定。

实测一轮 19 次亮灯里 **12 次**是这样半途中止的（63%）。

**修正**：改成"光一亮就记账"，在进入 FIRING 的同一拍调用 `mark_done`；
三条中止路径各加 `undo_done()` 回滚。另外判重改为按卡尔曼速度外推
（传送带上目标会移动，固定位置 + 固定半径必然失效）。

**教训**：先验证归因再改代码。半径这个假设之所以诱人，是因为改了确实有改善，
但那是掩盖而非修复。

### 3.4 修复引入的新故障：静态打靶失效

3.3 的修改上板后，静态场景出现「云台会对准，但激光完全不亮」。
两处成因都是前一次修改引入的：

| 成因 | 机理 | 修法 |
|---|---|---|
| 速度噪声 | 卡尔曼把检测框抖动读成运动（p90 达 22 px/s），外推 4 s 后把已打记录推出 90~150 px | 加速度死区 `vel_deadband = 30 px/s`，低于此值一律当 0 |
| 跳帧死锁 | "光一亮就记账"使 `weed_pending` 提前归零 → 静态画面触发跳帧 → `trk_coast` 置 `measured=0` → 联锁每拍拦截 | `if (weed_pending \|\| las.state != LS_IDLE) clear_cnt = 0;` |

**教训**：第二条是典型的跨模块耦合——改的是 `laser.cpp` 的记账时机，
坏的是 `detect_loop.cpp` 的调度判据，两者之间没有显式依赖，
只能靠上板实测暴露。已写入 `skill/04` 踩坑清单。

### 3.5 框图连线

**模型初稿**：箭头终点落在面板边框而非目标方框；UART 方向画反；反馈箭头退化成短线。

**修正**：重写连线函数，规定端点必须落在方框边缘坐标上；方向按"谁发起"定；
反馈路径改为整行下方走线，标签加白底遮罩。

**沉淀**：「端点必须在边上、标签不得遮挡箭头」写成生成脚本的硬约束。

## 四、边界与教训

1. **模型擅长结构与表达，不擅长判断"什么算实测"**。它会补齐看起来合理的数值，
   因此每次输出后都要逐项核对出处，对不上的一律删掉而不是留待查证。

2. **对自己有利的结果最危险**。3.2 那个 162× 如果没被拦下，会一直留在报告里，
   而且不容易被发现——它数值真实、推导过程也成立，错的是对照组的选取。

3. **排查前先质疑验收标准**。3.1 耗在五个假设上的时间，本可以用一句
   "bit-exact 对异构实现是否是合理要求"省掉。

4. **纠错要沉淀成规则**。上述每条最后都落成脚本约束或检查项，
   而不是只改这一次的产物——这就是 `skill/` 存在的理由。

5. **模型不能替代上板验证**。3.4 那两个故障在任何静态分析里都看不出来。
